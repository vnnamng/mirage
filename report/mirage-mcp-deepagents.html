The question and the verdict

You are wrapping a mirage Workspace (RAM and disk mounts plus a Pyodide python runtime) in an MCP server. The question is whether deepagents should then reach that server through a recreated workspace, meaning a custom backend on the deepagents side that implements deepagents' backend protocol and forwards every call over MCP, the way LangChain's own workspace abstraction would, or whether the MCP server should be treated as something else entirely.

Do not recreate the workspace on the deepagents side. Keep the in-process backend that this repo already uses, LangchainWorkspace(ws), and mount the MCP server on the same Workspace instance as a second door for external clients. The agent talks to the workspace through a typed protocol; outside tools talk to it through MCP. Nothing on the deepagents path goes over MCP.

A proxy backend over the existing six MCP tools would be strictly worse than what you have: that surface covers six of the eleven backend operations, returns prose meant for a model rather than data meant for a program, and carries a stale-write guard that would fire inside the agent's own backend.

If the workspace must leave the agent's process, mirror the full backend contract over MCP instead. Expose one tool per backend operation with structured results, and adapt them back into a remote backend object on the deepagents side. A prototype of that design in this repo passes the same conformance checks as the in-process adapter. It is the right migration path, not the starting point.

Both claims were verified with tests in this repo. A six-assertion test attaches both doors to one workspace and shows files written through either side visible through the other, with both execute paths serializing on the single Pyodide queue. A seventeen-assertion test runs the remote eleven-operation backend and the in-process adapter through identical checks. Details are in the wiring section.

How deepagents uses a backend

In deepagents 1.13.4 the backend is not just the storage behind the file tools. It is a single object that the whole middleware stack reads and writes, and every subagent shares it. Understanding who calls it is what makes a lossy proxy expensive.

Three facts matter for the decision.

  • The contract is typed and binary-safe. Directory listings come back as file-info records, reads can return bytes with a MIME type, and history offload uses batch upload and download of raw bytes.
  • The backend is probed constantly. On each model call and tool call deepagents resolves the backend and checks whether it has execute and delete. A backend with an empty id loses its execute tool without any error.
  • deepagents has no MCP client. The package contains no MCP code, the LangChain MCP adapter is not installed, and the only MCP package present is the server SDK that the mirage packages depend on.

What mirage already ships

The mirage-agents package already contains both halves of the recommended design, and this repo already uses one of them.

The deepagents adapter, already in use

LangchainWorkspace from @struktoai/mirage-agents/langchain implements the sandbox protocol directly against an in-process workspace. Every agent in this repo is created with it as the backend: the API test, the multi-tenant test and the chat CLI. It supplies all protocol methods except delete, and its sandbox id defaults to a non-empty string, so the execute tool is enabled and python3 runs inside Pyodide.

The MCP server, not yet used

createMirageMcpServer(ws) from @struktoai/mirage-agents/mcp turns any workspace into an MCP server, and serveMirageMcp connects it to standard input and output. It registers six tools built on the same tool-operations class that the OpenAI, Vercel, Mastra and Claude Agent SDK adapters use.

Four designs

A. In-process backend, MCP as a second door recommended

The deepagents contract is met in full through the existing adapter. Middleware offloads, memory and skills read the VFS directly with typed results. The MCP server costs one function call, and external clients get the tool descriptions and stale-write guard that were designed for them. Isolation between tenants stays where it is today: one workspace and one Pyodide heap per tenant.

B. Proxy backend over MCP, the recreated workspace not recommended

This is the design the question names, and it is the wrong layer. Beyond the gaps in the table above, the proxy would be re-instantiated or re-probed on every model and tool call, subagents would multiplex one pipe, and the adapter would have to track two moving contracts: deepagents' protocol, which has already gone from V1 to V2, and the mirage tool schema. It buys process separation at the price of a lossy wire, and there is a better way to get process separation.

C. MCP tools as plain tools next to the default state backend not recommended

Technically valid and strictly worse than A for more work. It is only sensible for read-only external services that are not the agent's filesystem, which is not this case.

D. Process-separated over a backend-shaped RPC when the host must change

This is the correct shape whenever the workspace must not run inside the agent's process. The move from A to D changes only the class behind the backend option; the agent, the prompts and the middleware are untouched. Design E below is D with MCP as the wire, and it is the concrete way to build it.

E. The full backend contract mirrored over MCP the migration path

Expose the workspace through eleven MCP tools, one per backend operation, each returning the operation's structured result verbatim with binary fields base64-encoded. On the deepagents side, adapt those eleven tools back into a backend object. This keeps everything design B loses, because the wire is shaped like the contract instead of like a chat tool.

Two readings of "adapt the eleven ops back into a new workspace" need separating. The one that works is the one drawn above: the adapted object is a backend, which is all deepagents needs. The other reading, mounting MCP-backed resources into a local mirage workspace with its own Pyodide, would make every python run re-seed every file over the wire, because Pyodide copies all mounts into its interpreter before each run. Keep the interpreter next to the files.

The prototype lives in src/mcp-backend-server.ts and src/remote-backend.ts, about 220 lines together, and is checked by tests/mcp-remote-backend.test.ts.

The hop overhead is about a tenth of a millisecond per operation on the in-memory transport. Over standard input and output or HTTP expect sub-millisecond to a few milliseconds plus network latency, which is small next to a model turn and next to Pyodide's per-run mount re-seed.

What E costs that A does not:

  • Base64 on every byte. JSON-RPC is text-framed, so binary offloads and downloads grow by a third on the wire. A private binary RPC would beat this only at large transfer volumes.
  • Timeouts and cancellation. The MCP client times out requests after sixty seconds by default; the prototype raises it to ten minutes. The backend's execute method takes no abort signal, so a hung python run can only be bounded by command limits on the workspace side.
  • Two tool sets in one process. The eleven backend tools must never reach a model: base64 upload, unguarded edit and raw execute are not model-safe. Serve them on a separate server or transport from the six LLM-facing tools.
  • Workspace selection. The prototype serves one workspace per server. Multi-tenant deployment means one server per tenant on standard input and output, or one streamable HTTP server that picks the workspace from the session.
  • Operational surface. Worker lifecycle, health and reconnects now exist. This is the price of process separation and is the same for D.

Recommendation

Choose A. The deepagents side keeps the object it already has. The MCP server is an additional door on the same workspace for clients that speak MCP: Claude Code, Claude Desktop, or another agent framework. The two doors are different contracts for different callers, and each already exists in the mirage-agents package.

Recreating a workspace on the deepagents side is never the right move when the wire is the mirage MCP tool set as shipped. The reason is structural rather than a bug list. Deepagents' backend is a storage and execution protocol consumed by middleware: file records, bytes, batch transfers, capability probes. Mirage's six MCP tools are a model-facing protocol: prose results and a guard against editing what you have not read. Proxying the first through the second loses information on every call and forces the proxy to parse prose back into data.

Mirroring the full contract over MCP, design E, is a different matter. It is the right way to do process separation when you need it, and the prototype shows it reaches parity with the in-process adapter. What it adapts back on the deepagents side is a backend object, not a workspace: no mounts and no interpreter are rebuilt next to the agent, which is exactly why it works. Choose it when one of the conditions below holds, and not before, because it adds a second process, a second tool set that must be kept away from models, and worker lifecycle you do not need while everything fits in one Node process.

When E (or D) becomes the right answer

  • The agent host must not run WebAssembly, for example a serverless or memory-constrained host.
  • A pre-warmed Pyodide pool should be shared across many short-lived agent runs, which the warm-runtime benchmark in this repo shows takes the first call from about 2.5 s to about 10 ms.
  • One tenant's runaway python must not stall other tenants' model turns. Pyodide runs on the Node main thread that the agent also runs on, and the watchdog caps a run but does not isolate it.
  • Scaling routes workspaces to machines by workspace id.

Cross-process sharing without any RPC is also available: a workspace backed by a shared state store, Redis or S3 keyed by workspace id, can be loaded in more than one process. That suits handoff between processes more than concurrent use, because each process runs its own Pyodide.

The migration from A to E is one line on the agent side, because the agent already talks to a backend object:

// today (A)
backend: new LangchainWorkspace(ws)

// later (E): the workspace lives in another process
const client = new Client({ name: 'agent', version: '1' })
await client.connect(new StdioClientTransport({ command: 'node', args: ['cli/mcp-backend.ts', 'workspaces/tenant.yaml'] }))
backend: new RemoteMirageBackend(client, { id: 'mirage', timeoutMs: 600_000 })

The wiring is the same three objects the test uses.

import { LangchainWorkspace, buildSystemPrompt } from '@struktoai/mirage-agents/langchain'
import { createMirageMcpServer, serveMirageMcp } from '@struktoai/mirage-agents/mcp'
import { loadWorkspace } from './src/config.js'

const { ws, mountInfo } = await loadWorkspace('workspaces/default.yaml')

// door 1: deepagents, exactly as cli/chat.ts does today
const agent = createDeepAgent({
  model,
  systemPrompt: buildSystemPrompt({ mountInfo }),
  backend: new LangchainWorkspace(ws),
})

// door 2: external MCP clients on the SAME ws
const mcp = createMirageMcpServer(ws, { name: 'mirage' })
await mcp.connect(transport)          // stdio, in-memory, or HTTP transport
// or, for a standalone stdio server: await serveMirageMcp(ws)

Optional refinements

  • Standalone MCP entry. A cli/mcp.ts that loads a workspace YAML and calls serveMirageMcp is the entry Claude Code or Claude Desktop would point at. Note that a server spawned by another client owns its own workspace; it shares state with an agent run only when both live in one process or through a shared state store.
  • Persistent memory across threads. Wrap the backend in a CompositeBackend with a StoreBackend routed at /memories/. The composite inherits the sandbox id from its default backend, so the execute tool survives.
  • Subclass to close the adapter's gaps. A small class extending LangchainWorkspace can add delete through the workspace's unlink, implement glob with directory components (the shipped one reduces patterns to a basename search), and let write overwrite like every built-in backend does.
import { CompositeBackend, StoreBackend } from 'deepagents'

const backend = new CompositeBackend(new LangchainWorkspace(ws), {
  '/memories/': new StoreBackend(),   // needs a `store` passed to createDeepAgent
})

Risks and gotchas

  • The sandbox id must be non-empty. Deepagents duck-types the execute capability on it. The adapter defaults to a non-empty id and a composite inherits it, but a hand-written backend that forgets it loses the execute tool without an error.
  • Permissions and execute conflict. Passing permissions with a sandbox backend throws unless every permission path is covered by a composite route. Do not combine permissions with the plain adapter.
  • Offload files land in the VFS. The filesystem middleware writes large tool results and evicted messages to /large_tool_results/ and /conversation_history/ at the workspace root. They become visible to python, to ls / and to external MCP clients, and Pyodide re-seeds them into the interpreter on every run, so the cost grows with each eviction. Give those prefixes a dedicated RAM mount, or route them through a composite to a state or store backend so they never touch the VFS.
  • One Pyodide queue for both doors. A long python run from an external client delays the agent's next turn and vice versa. The test shows runs serialize rather than interleave. If that matters, deny python from the external door through workspace policies, or move to design D.
  • The stale guard is one-sided. It protects external clients from editing what they have not re-read. The agent's backend has no such guard and can overwrite an external edit silently.
  • A session is not a narrowed workspace view. In mirage 0.0.6 a session is shell state, so the MCP server factory cannot be handed a narrowed session. Narrowing the external door today means workspace policies or a second workspace over the same resources, which needs its own verification.
  • Adapter quirks stay. Glob drops directory components, write refuses existing files so the model spends a turn switching to edit, and grep is literal with regex available through execute and rg.
  • Windows disk mounts. Subdirectories of a disk mount reach Pyodide without the execute bit, so python traversal fails. Prefer RAM mounts seeded from a directory, as the repo's README already notes.
  • Only the owner closes. Both doors hold the same workspace; the code that created it should be the only code calling close().
